### Purpose

To record the Customer's arrival for a Facility, Site, Activity, Batch, Personal Training session, or eligible service in a controlled and auditable way.

### Functional Requirement

The system shall allow authorized Reception Staff to record Customer check-in by identifying the Customer, validating eligibility, validating capacity, preventing duplicate active attendance, creating an Attendance record, capturing check-in timestamp and method, updating operational metrics, and recording audit events.

### Business Justification

Check-in is the operational proof that a Customer has consumed or begun consuming a service. Accurate check-in protects access control, capacity governance, billing integrity, customer history, and utilization reporting.

### Actors

- Reception Staff
- Customer
- Membership Service
- Capacity Service
- Notification Service
- Audit Service
- System

### Preconditions

- Organization, Facility, and Site are Active.
- Customer exists and is eligible for evaluation.
- Reception Staff is authenticated and authorized.
- Attendance rules are configured.
- Membership, service, session, and capacity context are available where applicable.

### Trigger

Reception Staff initiates check-in when a Customer arrives for service or presents a configured check-in identifier.

### In Scope

- Customer identification.
- Membership or service eligibility validation.
- Facility, Site, session, and capacity validation.
- Duplicate active attendance prevention.
- Check-in timestamp capture.
- Check-in method capture.
- Attendance record creation.
- Attendance history and audit recording.

### Out of Scope

- Walk-in fee collection.
- Membership purchase or renewal.
- Payment processing.
- Check-out recording.
- Attendance report generation.
- Permanent deletion of Attendance records.

### Inputs

- Organization ID
- Facility ID
- Site ID
- Customer reference
- Membership reference, where applicable
- Session reference, where applicable
- Check-in method
- Device reference, where applicable
- Staff remarks, where applicable

### Main Flow

1. Reception Staff opens Attendance Check-in.
2. The system loads Organization, Facility, Site, session, capacity, and attendance policy context.
3. Reception Staff identifies the Customer using a configured check-in method.
4. The system retrieves Customer, Membership, entitlement, and active Attendance context.
5. The system validates eligibility, capacity, duplicate attendance, and operational restrictions.
6. The system creates an Attendance record.
7. The system records check-in timestamp, method, Facility, Site, session, Customer, and Membership references.
8. The system updates operational occupancy and participation metrics.
9. The system emits business events and audit events.
10. The system displays check-in confirmation.

### Alternate Flows

- If manual search is used, Reception Staff selects the correct Customer before validation.
- If check-in is linked to a session, the Attendance record includes the Session Reference.
- If policy allows authorized override for capacity or eligibility, the system requires override permission and reason.
- If notification is disabled, check-in completes without sending Customer notification.

### Exception Flows

- If Customer is inactive, blocked, archived, or not found, check-in is rejected.
- If Membership or service eligibility fails, check-in is rejected unless authorized override is permitted.
- If capacity is exceeded, check-in is denied unless authorized override is permitted.
- If duplicate active Attendance exists, check-in is rejected or routed according to policy.
- If Attendance creation fails, no partial attendance state shall remain.

### Outputs

- Attendance record created.
- Attendance status set to Checked-In.
- Check-in timestamp and method recorded.
- Occupancy and participation metrics updated.
- Customer History updated.
- Audit events recorded.
- Notifications generated where configured.

### UI Behaviour

Attendance Check-in shall support rapid Customer lookup, scanner input, mobile number search, QR/barcode/RFID input, eligibility status indicators, capacity warnings, duplicate warnings, and a clear check-in success confirmation.

### Purpose

To determine whether a Customer is permitted to access a service based on Membership, Facility, Site, session, capacity, and restriction rules.

### Functional Requirement

The system shall validate Membership eligibility before attendance approval by checking Customer status, Membership status, validity dates, entitlement scope, Facility/Site eligibility, session eligibility, outstanding restrictions, duplicate attendance, and capacity constraints.

### Business Justification

Eligibility validation prevents unauthorized service access, protects revenue, enforces operating policies, and ensures attendance records reflect valid service consumption.

### Actors

- System
- Reception Staff
- Trainer
- Membership Service
- Customer Service
- Capacity Service
- Audit Service

### Preconditions

- Customer reference is available.
- Membership or service entitlement context is available where applicable.
- Facility, Site, and session context are available.
- Attendance validation policies are configured.
- System can access relevant Membership and capacity data.

### Trigger

Eligibility validation is triggered during check-in, session attendance, walk-in conversion checks, attendance correction, or access validation API calls.

### In Scope

- Customer status validation.
- Membership status validation.
- Validity period validation.
- Facility/Site entitlement validation.
- Session eligibility validation.
- Capacity validation.
- Duplicate active attendance validation.
- Restriction validation.

### Out of Scope

- Membership creation.
- Payment collection.
- Customer registration.
- Attendance history display.
- Report generation.

| Membership ID | Membership entitlement | Identifier | Conditional | User / System | Must be Active or grace-eligible | Required for membership attendance |
| Facility ID | Facility access context | Identifier | Yes | User / Session | Must be Active and eligible | Capacity scope |
| Site ID | Site access context | Identifier | Conditional | User / Session | Must be Active and eligible | Site scope |
| Session ID | Scheduled session context | Identifier | Conditional | User / Session | Must permit Customer | Session attendance |
| Validation Result | Eligibility outcome | Structured Data | Yes | System | Eligible, Warning, Denied | Drives check-in |
| Denial Reason | Reason for failed validation | Text | Conditional | System | Required if denied | Safe display |

### Main Flow

1. The system receives an attendance eligibility request.
2. The system validates Organization, Facility, Site, and user scope.
3. The system retrieves Customer status and restriction context.
4. The system retrieves Membership status, validity, entitlement, and service scope where applicable.
5. The system evaluates Facility, Site, session, capacity, and duplicate attendance rules.
6. The system determines whether attendance is Eligible, Eligible With Warning, Requires Override, or Denied.
7. The system returns validation result with safe reason details.
8. The system records validation audit event where configured.

### Alternate Flows

- If Customer has multiple active Memberships, the system selects or prompts for the applicable entitlement.
- If grace period applies, validation may return Eligible With Warning.
- If configured override is available, validation returns Requires Override rather than Denied.
- If walk-in is allowed, validation may route to Walk-in Attendance rather than Membership Attendance.

### Exception Flows

- If Membership data is unavailable, validation fails safely.
- If Customer scope cannot be verified, validation is denied.
- If Facility, Site, or session is inactive, validation is denied.
- If capacity service is unavailable, validation follows Organization fail-safe policy.

### Outputs

- Eligibility result.
- Applicable Membership or entitlement reference.
- Denial or warning reason.
- Override requirement where applicable.
- Validation audit event.

### UI Behaviour

The UI shall display eligibility using clear status indicators, denial reasons, warnings, and override prompts. Sensitive restriction details shall be masked unless the user has permission.
