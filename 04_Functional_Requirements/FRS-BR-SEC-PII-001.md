# BR-SEC-PII-001 — PII Storage: Hashing vs Encryption (Security)

Status: Draft
Owner: BA-Team (provisional)

Purpose:
Define a mandatory approach for storing personal and important data (PII) in the database to reduce risk of accidental leakage while preserving required business functionality.

Rule statement:
- All personal data elements MUST be protected at rest. The protection mechanism depends on retrieval needs:
  - If the original value never needs to be recovered (one-way verification only), store a salted, slow hash (e.g., Argon2id) with per-record salt and an application-level `pepper` kept in a secure key store.
  - If the original value must be recovered or re-used (lookup, display, legal request), store the value encrypted using authenticated, envelope encryption with keys managed by the organisation's KMS (deterministic encryption only when necessary for equality lookups; otherwise use randomized AEAD encryption).

Scope:
- Applies to all systems writing personal data into primary or secondary persistent stores (databases, data lake, caches). Examples: email addresses, national IDs, credit card PAN (note: PCI rules for card data), phone numbers, addresses, and any sensitive identifiers.

Standards / Algorithms:
- Passwords: use Argon2id (recommended) or bcrypt/scrypt with per-record salt; never use plain SHA-family for passwords.
- One-way hashed PII (non-recoverable): Argon2id with per-record unique salt (≥16 bytes) and application pepper stored in KMS.
- Recoverable PII: AES-256-GCM or ChaCha20-Poly1305 via envelope encryption. Use KMS to store and rotate data encryption keys (DEKs); DEKs should be wrapped by KMS-managed key (KEK).
- Deterministic encryption (for equality search): use a vetted deterministic AEAD mode or HMAC-based tokenization; restrict to cases where necessary and document justification.

Key management:
- Use a central Key Management Service (KMS) for KEKs and rotation policies.
- Limit access to unwrapped DEKs to small, audited service components.
- Implement key rotation with re-encryption or re-wrapping strategies and document migration steps.

Indexing & Search:
- Do not store plaintext for indexed searches. For equality search where necessary, store a deterministic HMAC (with key from KMS) alongside encrypted value; protect HMAC keys and document the threat model.

Data retention & deletion:
- On deletion requests, remove encrypted values and associated derivatives (hashes/HMACs). For immutability requirements, document the legal retention strategy and access controls.

Audit & Logging:
- Logging must not contain raw PII. Any debug or error logs that include PII must be redacted before persistence.

Acceptance tests:
1. Attempt to retrieve stored PII from DB without KMS access — original value must not be derivable.
2. Validate that password verification and deterministic-match flows succeed while plaintext is unrecoverable from storage alone.

Implementation notes:
- Developers must use platform encryption libraries and KMS SDKs; do NOT implement custom crypto.
- Store per-record salt as metadata; store pepper and KEKs in KMS, not in repo or environment variables.

Compliance notes:
- Follow PCI, GDPR, HIPAA or other region-specific regs where applicable. This BR complements compliance controls but does not replace legal review.
