### Purpose

To create a centralized Customer record under one Organization so the Customer can purchase memberships, attend services, make payments, receive notifications, and maintain a complete relationship history.

### Functional Requirement

The system shall allow authorized Reception Staff to register a Customer with mandatory profile, contact, emergency contact, primary Facility, primary Site, communication consent, duplicate validation, Customer ID generation, notifications, and audit history.

### Business Justification

Customer registration is the starting point for the customer value journey and ensures every downstream membership, attendance, billing, payment, personal training, notification, and support activity is linked to a unique, auditable Customer record.

### Actors

- Reception Staff
- Customer
- Organization Administrator
- Notification Service
- Audit Service
- System

### Preconditions

- Organization exists and is Active.
- Facility and Site context are available where applicable.
- Reception Staff is authenticated.
- Reception Staff has Customer registration permission.
- Customer management policies are configured.
- Duplicate validation rules are available.

### Trigger

Reception Staff selects Register Customer when a new Customer visits, calls, books, or requests service.

### In Scope

- Capture Customer personal information.
- Capture Customer contact details.
- Capture mandatory emergency contact details.
- Assign primary Facility and Site.
- Capture communication consent.
- Generate unique Customer ID.
- Prevent duplicates according to configured rules.
- Set initial Customer status.
- Record customer history and audit events.

### Out of Scope

- Membership purchase.
- Payment collection.
- Attendance recording.
- Customer portal account creation.
- Staff account creation.
- Cross-Organization customer transfer.

### Inputs

- Organization ID
- Full name
- Mobile number
- Email address
- Date of birth or age
- Gender
- Address
- Emergency contact details
- Primary Facility
- Primary Site
- Communication preferences
- Identity proof details, if provided
- Photograph, if provided
- Medical information, where applicable

### Field Definitions

| Field Name | Description | Data Type | Mandatory | Source | Validation | Notes |
|---|---|---|---|---|---|---|
| Customer ID | Unique customer identifier | Identifier | Yes | System | Globally unique and never reused | Generated by Digitize |
| Organization ID | Owning Organization | Identifier | Yes | Session / System | Must be Active and authorized | Customer belongs to one Organization |
| Full Name | Customer legal or display name | Text | Yes | Reception Staff / Customer | Required and length validation | Used across customer records |
| Mobile Number | Primary contact number | Phone | Yes | Reception Staff / Customer | Format and duplicate validation | Primary duplicate check |
| Email Address | Customer email | Email | No | Reception Staff / Customer | Format validation | Used for notifications |
| Date of Birth / Age | Customer age reference | Date / Number | Yes | Reception Staff / Customer | Required by policy | Supports eligibility rules |
| Gender | Customer gender | Enum | Yes | Reception Staff / Customer | Must use configured value | Required by BA-02 |
| Emergency Contact | Emergency contact details | Structured Data | Yes | Reception Staff / Customer | Name, relationship, and mobile required | May be maintained separately |
| Primary Facility | Customer primary service Facility | Identifier | Yes | Reception Staff | Must be Active and authorized | Operational context |
| Primary Site | Customer primary Site | Identifier | Conditional | Reception Staff | Must belong to selected Facility | Required where Site operations apply |
| Communication Consent | Communication permission preferences | Structured Data | Yes | Reception Staff / Customer | Consent rules must be captured | Required before promotional communication |

### Main Flow

1. Reception Staff opens Customer Registration.
2. The system loads Organization, Facility, Site, mandatory field, consent, and duplicate validation rules.
3. Reception Staff enters Customer personal, contact, address, emergency contact, and operational context details.
4. The system validates required fields, format rules, age rules, duplicate identity, Facility/Site eligibility, and consent requirements.
5. The system generates a unique Customer ID.
6. The system creates the Customer record under the Organization.
7. The system sets Customer status according to registration and verification policy.
8. The system creates initial Customer History entry.
9. The system sends registration notification where configured.
10. The system records audit events and displays registration confirmation.

### Alternate Flows

- If identity verification is required before Active status, the Customer may be registered in Registered or Prospect status.
- If duplicate warning is possible but policy permits continuation, the system requires authorized confirmation.
- If optional identity proof or photograph is unavailable, the Customer can be registered where policy allows and marked incomplete for follow-up.

### Exception Flows

- If mandatory information is missing, registration is blocked.
- If duplicate Customer is found and duplicates are not permitted, registration is rejected.
- If selected Facility or Site is inactive or unauthorized, registration is blocked.
- If Customer ID generation fails, registration is cancelled and logged.
- If notification fails, registration remains valid and notification failure is recorded.

### Outputs

- Customer record created.
- Unique Customer ID generated.
- Initial Customer status assigned.
- Emergency contact captured.
- Communication consent captured.
- Customer History entry created.
- Notifications and audit events recorded.

### UI Behaviour

Customer Registration shall support quick entry, duplicate search prompts, mandatory field indicators, inline validation, Facility/Site selectors, consent capture, emergency contact entry, and confirmation summary. Save shall remain disabled until mandatory fields are valid.

### Purpose

To validate Customer identity where required by Organization policy before permitting dependent membership or service activation.

### Functional Requirement

The system shall allow authorized users to record Customer identity verification requests, documents, verification outcomes, rejection reasons, notifications, and audit history.

### Business Justification

Identity verification reduces duplicate, fraudulent, or incomplete Customer records and supports compliance, safety, membership eligibility, and risk management.

### Actors

- Reception Staff
- Customer
- Organization Administrator
- Approval Workflow Service
- Notification Service
- Audit Service

### Preconditions

- Customer exists.
- Customer belongs to authorized Organization scope.
- Identity verification policy is configured.
- User is authenticated.
- User has identity verification permission.
- Required identity documents are available where applicable.

### Trigger

Reception Staff starts verification from Customer Profile, registration follow-up, or membership eligibility review.

### In Scope

- Capture identity document details.
- Upload identity proof where required.
- Mark verification status.
- Record rejection reason.
- Block dependent processes where verification is required and incomplete.
- Notify Customer and staff.
- Record audit and Customer History.

### Out of Scope

- External government verification integration unless configured in future.
- Customer registration.
- Membership activation processing.
- Payment validation.
- Legal adjudication.

### Inputs

- Customer ID
- Identity document type
- Identity document number
- Document file
- Verification status
- Verification notes
- Rejection reason
- Verification date

### Field Definitions

| Field Name | Description | Data Type | Mandatory | Source | Validation | Notes |
|---|---|---|---|---|---|---|
| Customer ID | Customer being verified | Identifier | Yes | System | Must exist and match scope | Target record |
| Document Type | Identity proof type | Master Data | Yes | Reception Staff | Must be configured and active | Aadhaar, Passport, Driving License, Government ID |
| Document Number | Identity proof number | Text | Conditional | Reception Staff / Customer | Format based on document type | Sensitive data |
| Document File | Uploaded identity document | File | Conditional | Reception Staff / Customer | File type, size, malware scan | Stored securely |
| Verification Status | Verification outcome | Enum | Yes | Reception Staff / System | Pending, Verified, Rejected | Lifecycle of verification |
| Verification Notes | Supporting comments | Text | No | Reception Staff | Length validation | Audit context |
| Rejection Reason | Reason for failed verification | Text | Conditional | Reception Staff | Required when Rejected | Customer-facing rule may mask details |

### Main Flow

1. Reception Staff opens Customer Identity Verification.
2. The system loads Customer profile, verification requirements, supported document types, and current verification status.
3. Reception Staff captures document details and uploads proof where required.
4. The system validates document type, metadata, file security, Customer status, and permissions.
5. Reception Staff submits verification result or request.
6. If verification passes, the system marks identity as Verified.
7. If verification fails, the system marks identity as Rejected and captures reason.
8. The system updates dependent eligibility indicators.
9. The system records Customer History and audit events.
10. The system sends verification notifications.

### Alternate Flows

- If verification is not required by policy, Customer can proceed without verification status.
- If verification requires approval, the system routes the request to an authorized approver.
- If document upload is deferred, verification remains Pending.

### Exception Flows

- If required document information is missing, verification cannot be completed.
- If uploaded file fails validation, upload is rejected.
- If verification is Rejected, dependent membership activation may be blocked.
- If user lacks permission, action is denied and logged.

### Outputs

- Customer verification status updated.
- Customer Verification record created or updated.
- Customer History entry.
- Eligibility indicators updated.
- Notifications and audit events.

### UI Behaviour

Identity Verification shall display current verification status, required documents, upload controls, verification decision controls, rejection reason field, and dependent eligibility warnings.

### Purpose

To retire a Customer from active operational use while preserving membership, attendance, billing, payment, document, notification, and audit history.

### Functional Requirement

The system shall allow an Organization Administrator to archive an eligible Customer after validating archival constraints, restricting future transactions, preserving historical records, notifying stakeholders, and auditing the lifecycle action.

### Business Justification

Customer archival supports long-term record management and compliance without deleting transactional history or compromising auditability.

### Actors

- Organization Administrator
- Reception Staff
- Customer
- Reporting Service
- Notification Service
- Audit Service

### Preconditions

- Customer exists.
- Customer is not already Archived.
- User is authenticated.
- User has Customer archival permission.
- Retention and archival policies are configured.
- Archival eligibility checks are available.

### Trigger

Organization Administrator selects Archive Customer from Customer Status Management.

### In Scope

- Validate archival eligibility.
- Capture archival reason.
- Change Customer status to Archived.
- Block new operational transactions.
- Preserve historical business records.
- Provide read-only historical access where permitted.
- Notify stakeholders.
- Record audit and Customer History.

### Out of Scope

- Physical deletion of Customer data.
- Data purging.
- Membership cancellation.
- Refund processing.
- Payment deletion.
- Cross-Organization data movement.

### Inputs

- Archive reason
- Archive category

- Internal notes

### Main Flow

1. Organization Administrator opens Customer Status Management.
2. Organization Administrator selects Archive Customer.
3. The system validates Customer status, permission, open dependencies, active memberships, unpaid invoices, active bookings, and retention rules.
4. The system displays archival impact and blockers.
5. Organization Administrator enters archive reason and confirms archival.
6. The system changes Customer status to Archived.
7. The system blocks new operational Customer transactions.
8. The system preserves historical records across membership, attendance, billing, payment, personal training, notification, and audit domains.
9. The system creates Customer History and audit entries.
10. The system sends archival notifications.

### Alternate Flows

- If unresolved blockers exist, archival is blocked and remediation guidance is displayed.

### Exception Flows

- If historical transactions exist, physical deletion is blocked and archival is used instead.
- If active dependencies prevent archival, archival is blocked.
- If user lacks permission, action is denied and logged.

### Outputs

- New transactions blocked.
- Historical records preserved.
- Customer History entry.
- Notifications.
- Audit events.

### Purpose

To provide an immutable timeline of Customer interactions and business history across registration, profile changes, memberships, attendance, payments, billing, personal training, notifications, and support.

### Functional Requirement

The system shall allow authorized users to view, filter, search, and export Customer History according to data scope, privacy, retention, and audit access rules.

### Business Justification

Customer History supports relationship management, customer service, dispute resolution, audit readiness, operational continuity, and long-term business insights.

### Actors

- Reception Staff
- Organization Administrator
- Finance Staff
- Trainer
- Support Executive
- Customer
- Audit Service
- Reporting Service

### Preconditions

- Customer exists.
- User is authenticated.
- User has Customer History view permission.
- Customer History records exist or empty-state handling is available.
- User scope covers the Customer.

### Trigger

Authorized user opens Customer History from Customer Profile or related operational context.

### In Scope

- Display Customer lifecycle timeline.
- Display profile update history.
- Display membership, attendance, billing, payment, personal training, notification, and support summaries where permitted.
- Filter by date and category.
- Export history where permitted.
- Enforce immutability and audit access.

### Out of Scope

- Editing history records.
- Deleting history records.
- Correcting source transactions.
- Full module-specific detailed reports.
- Customer data purging.

### Inputs

- Customer ID
- Date range
- History category
- Facility or Site filter
- Related entity filter
- Export request

### Field Definitions

| Field Name | Description | Data Type | Mandatory | Source | Validation | Notes |
|---|---|---|---|---|---|---|
| Customer ID | Customer history subject | Identifier | Yes | User selection | Must exist and match scope | Primary context |
| Date Range | Timeline period | Date Range | Yes | User | Must be valid and within limits | Required |
| History Category | Type of history event | Enum | No | User | Must be supported category | Membership, attendance, billing, etc. |
| Facility Filter | Facility context | Identifier | No | User | Must be authorized | Optional |
| Site Filter | Site context | Identifier | No | User | Must be authorized | Optional |
| Export Request | Export action | Boolean | No | User | Requires export permission | Optional |

### Main Flow

1. Authorized user opens Customer History.
2. The system validates Customer scope, permission, and audit access rules.
3. User enters date range and optional filters.
4. The system retrieves Customer History and related summary events from permitted modules.
5. The system masks sensitive details where permission is insufficient.
6. The system displays immutable timeline entries with source module, timestamp, actor, event, and outcome.
7. User exports history where permitted.
8. The system records history view or export audit events.

### Alternate Flows

- If no history exists for filters, an empty state is displayed.
- If user has Customer-facing access in future, only customer-visible history is shown.
- If related module source is unavailable, the system displays available history and marks missing source.

### Exception Flows

- If user lacks history permission, access is denied and logged.
- If date range exceeds configured limit, query is blocked.
- If export fails, failure is logged and retry guidance is displayed.
- If sensitive events are restricted, entries are masked or hidden.

### Outputs

- Customer History timeline.
- Filtered event list.
- Export file where permitted.
- Audit event for history access.

### UI Behaviour

Customer History shall display chronological timeline, filters, category chips, source module labels, actor/outcome indicators, pagination, and export controls. Entries shall be read-only.
